# 微元 1.0 首批验收用例

评审稿 · 2026-11-16

## 1. 拓客实测

用三条原始输入分别启动数字员工。使用 `deepseek-flash` 将需求转成结构化条件，使用 DeepSeek Search 和按需 Fetch 找到可引用的公域证据。记录候选企业数、人工确认有效的线索数、可用的公开商务联系方式覆盖率、调用数、实际费用和耗时。每条结果应包含企业或门店名称、市场、关联产品或采购理由、原文链接，以及可取得的证据日期。

| 编号 | 原始输入 | 验收标准 |
| --- | --- | --- |
| LEAD-01 | 我是一家中国生产LED的工厂，需要找10家美国地区有LED采购需求的客户。 | 目标为 10 家可核验的不同采购主体。每家至少有一条能证明其 LED 相关采购需求的公开证据，例如招标、采购公告或明确的供应商招募。仅有产品目录或渠道关系的企业可展示为潜在线索，并单独统计。若公开证据不足，标明已核验数量及缺口。LED 产品范围暂按 LED 相关品类检索，并记录实际匹配的是器件、模组、灯具或其他子类。 |
| LEAD-02 | 我是中国运动水杯的生产商，需要找一批法国地区线下门店，如健身房、户外运动用品店、商超、便利店 | 按健身房、户外运动用品店、商超、便利店分组，核对法国实体门店地址及渠道匹配理由。健身房注明可核实的零售或周边销售线索。区分门店与所属品牌或总部，附可取得的官方门店页及商务联系入口。总数量由本次任务设定，逐类报告覆盖情况。 |
| LEAD-03 | 我是生产汽车零部件的厂商，主营产品是汽车轮胎，海关编码是401110，需要找俄罗斯的采购商，数量5家 | 保留用户给出的 HS `401110`，核对证据里的乘用车轮胎品类。目标为 5 家有俄罗斯市场采购证据的不同主体。公开采购公告、供应商征集和企业级海关记录分别注明证据类型。仅有销售目录的经销商可作候选并单独统计。若用户显式选择海关核验，先复用有效证据，再按预算执行。 |

共通负面场景包括同名实体、重复转载、已结束的招标、匹配同一品牌的多家门店、来源无法打开及搜索无结果。关闭的招标计为历史证据，仍有效的公开采购需求单独标识。仅取得搜索摘要的结果计为待核验。预算内未达到目标数量时，交付已有结果和覆盖缺口。LEAD-03 按 `401110` 对应的汽车用新充气橡胶轮胎品类核验。[联合国统计司 HS 分类](https://unstats.un.org/unsd/classifications/Econ/Structure/Detail/EN/2089/4011)

## 2. 注册赠点与按操作扣点

| 编号 | 操作 | 预期结果 |
| --- | --- | --- |
| PTS-01 | 测试环境使用中国大陆手机号、密码及验证码 `123456` 完成注册 | 创建账号、默认工作空间和点数钱包，同时生成一笔 1,000 点的注册赠送流水。注册完成后可登录并发起体验权益范围内的拓客。 |
| PTS-02 | 同一号码以本地格式和 `+86` 格式重复注册或重放请求 | 号码规范化后只存在一个账号和一笔赠送记录。 |
| PTS-03 | 执行一项未覆写扣点的业务操作，再执行一项配置不同扣点的业务操作 | 默认报价及结算为 1 点。已配置的操作采用相应配置，后续改价只对新提交生效。后台人民币参考标价为 1,000 点对应 100 元。 |
| PTS-04 | 余额仅够一次操作时发起两个并发请求，再重放其中一个 | 仅一个请求成功预占点数。重放返回原任务，余额与流水可对账。 |
| PTS-05 | 模拟任务成功、部分成功、失败和取消 | 核对任务状态、按版本结算点数和剩余点数释放。模拟外部扣费状态未知，供应商对账与用户点数流水可分别追踪。 |
| PTS-06 | 用另一个工作空间的账号查询余额、线索和流水 | 服务端拒绝跨租户访问。 |
| OTP-01 | 在 `APP_ENV=test` 下申请挑战并提交 `123456`。再重放同一挑战，或使用错误手机号、错误验证码或过期挑战。 | 正确验证码仅验证成功一次。重放、错号、错码和过期均验证失败。 |
| OTP-02 | 在未启用测试模式且没有正式供应商的环境调用两个接口 | 接口返回 `503`，固定验证码无法通过验证。 |
