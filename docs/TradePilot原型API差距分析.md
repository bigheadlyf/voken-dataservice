# TradePilot 原型 API 差距分析

核对日期：2026-11-18。

原型：https://tradepilot-partner-club-demo.rubyguild2.chatgpt.site/

对照范围：当前工作区代码（包含尚未提交的员工对话功能），不是线上服务的部署验收。原型明确标注所有资料、邮件和动作均为本地模拟；以下是由实际页面交互推导的接口设计建议，路径尚未实现。

## 结论

已有能力覆盖“建员工 → 对话调整配置 → 提交一次拓客任务 → 看线索和报告”。原型要求补齐“确认开发约定 → 持续研究 → 独占客户跟进 → 邮件联系和追问 → 判断采购需求 → 用户接手 → 反馈学习”的完整流程。

主要新增模块是公司共享记忆、开发约定及策略、持久客户库、开发看板、邮件收发、交接和学习反馈。员工 CRUD、聊天、搜索、报告及点数接口应复用和扩展。

以下业务路径省略统一前缀 `/api/v1/workspaces/{workspace_id}`。`{id}` 需按所在资源解释；供应商回调单独列出。

## 已有接口与适配范围

| 原型功能 | 已有接口 | 需要补充的行为 |
| --- | --- | --- |
| 新增、查看、改名、解雇员工 | `POST/GET /agents`、`GET/PATCH/DELETE /agents/{agent_id}` | 创建支持员工模板、风格、买家类型；新员工读取公司共享知识；解雇停止外联并处理客户归属 |
| 与伙伴聊天 | `POST /agents/{agent_id}/messages`、会话及消息查询 | 加载共享记忆和开发约定；返回结构化待确认动作及业务资源 ID；接入新增业务工具 |
| 找客户与调查 | `POST /agents/{agent_id}/runs`、`GET /jobs`、`GET /jobs/{job_id}`、`GET /jobs/{job_id}/leads` | 当前是一次任务，不能直接表达长期开发；结果需要沉淀到独立客户库 |
| 暂停开发 | `POST /agents/{agent_id}/pause` | 现在只暂停员工并取消活动任务；需同时阻止未来定时外联，并在发送前复核状态 |
| 客户研究与核验 | `/public-searches`、`/buyer-enrichments`、`/customs-verifications`、`/reports` | 研究和报告绑定稳定 customer_id，保存来源及时间，不只依赖 job_id + lead_index |
| 点数及计费 | `GET /points`、`/points/ledger`、`/points/costs` | 若新增收费动作，扩展操作类型和预算控制；本原型没有充值页，不列入首期页面缺口 |

代码依据：`app/workspaces.py` 的路由、`app/chat.py` 的聊天与工具注册、`app/db.py` 的表结构、`app/worker.py` 的队列和 `app/pipeline.py` 的检索流程。

## P0：实现原型主流程必须补齐

### 1. 公司共享记忆

原型“记住的事”包含产品用途、公司优势、默认买家方向、承诺边界，支持更正与忘记，展示来源和版本。公司页和员工资料页复用这份知识，员工更换后保留。

| 建议接口 | 用途 |
| --- | --- |
| `GET /company/memories` | 公司事实列表，返回 key、value、version、来源会话/消息、更新时间、核实状态 |
| `POST /company/memories` | 对话或用户新增公司事实，记录来源 |
| `PATCH /company/memories/{memory_id}` | 更正事实，带 expected_version 防止覆盖并发修改 |
| `DELETE /company/memories/{memory_id}` | 忘记事实，使其退出后续模型上下文与策略依据 |

当前 `AgentMemory` 主键包含 agent_id，仅有 key/value；`remember/recall/forget` 是员工工具，没有共享记忆管理 HTTP API。保留员工个人偏好，另增工作空间级公司事实，不能直接把员工记忆列表当作公司知识库。

记忆的来源和版本不等于已核实。认证、MOQ、交期等须能标记 unknown/unverified/confirmed；忘记或更正被策略引用的事实后，应使相关策略重新核对，不能继续按旧事实对外承诺。忘记也不应删除已发生的客户邮件记录。

### 2. 开发约定、启动与恢复

原型通过对话总结产品、优势、目标买家和销售边界，用户确认后才开始自动开发。“修改员工配置”和“授权持续外联”需要分别建模。

| 建议接口 | 用途 |
| --- | --- |
| `GET /agents/{agent_id}/development-plan` | 查询约定草案、版本和确认状态 |
| `PUT /agents/{agent_id}/development-plan` | 保存产品、市场、买家类型、承诺边界、人工确认事项、跟进时段、汇报规则 |
| `POST /agents/{agent_id}/development-plan/confirm` | 确认指定 plan_version，冻结本轮执行依据并启用开发 |
| `POST /agents/{agent_id}/resume` | 在有效约定和预算内恢复开发，与一次性 `/runs` 区分 |

扩展已有 `/pause`，暂停研究/追问调度及待发送动作。市场、预算、产品承诺发生实质变化时生成新草案；不得让模型直接覆盖已确认约定并扩大执行范围。对话“可以”应绑定具体待确认版本，避免确认对象不明。

原型没有完整预算设置页，但真实持续运行需要服务端保存预算和调用上限；已有“每次请求 confirm_paid”不能直接当作长期付费授权。

### 3. 独立客户库与归属控制

原型明确“同一位客户只由一位伙伴联系”，公司页保留客户记录，员工替换不删除客户。当前线索是 `Job.result` 中的数组，没有稳定客户 ID、负责人和跨任务跟进状态。

| 建议接口 | 用途 |
| --- | --- |
| `GET /customers` | 公司客户列表，支持 agent_id、阶段、跟进主体、分页筛选 |
| `GET /customers/{customer_id}` | 企业、联系人、来源证据、适配判断、需求、负责人及下一步 |
| `PATCH /customers/{customer_id}` | 纠正客户和联系人信息，按字段限制修改，不能绕过接手/拒联动作 |
| `POST /customers/{customer_id}/assignment` | 变更负责员工，事务内保证单一有效跟进归属 |

客户创建可由检索任务内部 upsert 完成，原型没有手动建客页面，不必为了 CRUD 完整额外开放创建接口。去重使用域名、标准化企业身份、供应商企业 ID 等证据；不要只按企业名合并，也不要把唯一约束设成“每个员工一份客户”。

客户至少分开保存：研究状态、跟进状态、需求判断、跟进主体（agent/human）和禁止联系标记。用户接手不等于成交；沉默不等于需求；明确拒联优先于恢复开发和重新分配。

### 4. 开发进度与经过

| 建议接口 | 用途 |
| --- | --- |
| `GET /agents/{agent_id}/development` | 页面聚合：当前约定、运行状态、客户卡片、待接手事项、下一步和阻塞原因 |
| `GET /agents/{agent_id}/development/events` | “开发经过”：研究、筛选、发信、收信、追问、交接等业务事件，支持 cursor 分页 |

客户卡片返回 customer_id、当前阶段、理由、last_activity_at、next_action_at、thread_id；待接手卡返回采购原话、联系人、需求产品/数量/时间、证据引用及缺失项。分页时不要把历史全量塞进一个响应。

可先轮询聚合接口；SSE/长连接作为后续体验优化。现有 jobs 查询继续用于底层异步任务诊断，不能替代客户级业务状态。

### 5. 邮件收发与自动追问

原型“往来邮件”展示完整收发记录；用户接手后可直接回复，交回伙伴后恢复自动跟进。当前项目未发现邮件账户、邮件线程、投递任务或入站处理能力。

| 建议接口 | 用途 |
| --- | --- |
| `GET /mail/accounts` | 查询可用发件账户和连接状态 |
| `POST /mail/accounts/connect` | 启动选定邮件供应商的授权；具体回调按接入方案确定 |
| `GET /mail/threads?customer_id=...&agent_id=...` | 客户邮件线程列表，支持分页 |
| `GET /mail/threads/{thread_id}/messages` | 主题、正文、发件人、收件人、时间、方向及投递状态 |
| `POST /mail/threads/{thread_id}/messages` | 人工回复邮件，返回发送任务和状态，不把排队当作已送达 |

供应商系统接口（不使用上面省略的工作空间路径）：

| 建议接口 | 用途 |
| --- | --- |
| `POST /api/v1/integrations/mail/{provider}/webhook` | 接收回信、投递结果、退信等事件；验签并按事件 ID 去重，服务端由账户确定工作空间 |

如果首期只用平台预配置邮箱，可以先提供账户状态查询，把自助连接接口后移。收信若供应商无 webhook，可由后台轮询实现；前端仍使用统一邮件接口。

生成开发信、自动发送、自动追问应由后台业务服务和 Agent 工具调用，不必给前端各暴露一个按钮接口。需要持久化发件 outbox、供应商消息 ID、发送尝试、定时追问、客户时区和间隔。发送执行前再次检查有效约定、客户归属、暂停、接手、预算、拒联和是否已有新回复，避免过时的排队动作发出。

### 6. 人工接手与交回

| 建议接口 | 用途 |
| --- | --- |
| `POST /customers/{customer_id}/takeover` | 对应“我来接手”“由我跟进”；转人工并取消该客户待发送和追问 |
| `POST /customers/{customer_id}/return-to-agent` | 对应“交回伙伴继续跟进”；校验员工有效、约定有效、无拒联后恢复 |
| `POST /customers/{customer_id}/follow-up-requests` | 对应“继续替我了解”；记录要补充的问题，并由后台安排跟进 |

交接写入业务事件并使用幂等键；与发送竞争时需要事务或等效的并发控制。不能用普通 `PATCH owner` 后再异步取消来承诺“接手即停止”。已经提交给供应商的邮件无法保证撤回，应明确返回在途情况。

## P1：补全“打法—反馈—学习”

### 7. 本轮打法与学习记录

| 建议接口 | 用途 |
| --- | --- |
| `GET /company/strategies?agent_id=...` | “本轮打法”：研究标准、开场理由、追问分支、停止规则、版本及依据 |
| `GET /company/learnings` | “学到的经验”：结论、来源案例、证据、适用市场和产品、样本范围 |
| `POST /customers/{customer_id}/feedback` | 保存“确实有采购需求”“还没到接手阶段”等反馈及可选说明 |

打法是根据已确认约定生成的可解释执行方案；首期可以后台生成，未观察到独立打法编辑器，不要求先做策略 CRUD。反馈不应直接修改历史客户原话；更新策略需记录来源和版本，不自动扩大授权。小样本经验不能表述成已验证的市场效果。

### 8. 员工模板及首页适配

- 可新增 `GET /agent-templates` 返回员工显示名、风格、头像和可用状态；若员工固定且不运营配置，也可先由前端静态维护。
- 扩展 `POST /agents` 接收 template_id、market、buyer_type，服务端生成默认 instructions，避免新增员工弹窗缺少现有必填字段。
- 扩展员工列表/详情返回职责摘要、开发状态和是否有待接手客户；不必为首页另建一套员工 CRUD。
- 解雇时停止新外联、解除或转移客户归属，保留公司事实、客户、邮件和来源。现有 DELETE 是软删除，但没有客户转移流程；归属处理要补齐。

## 推荐实施顺序

1. 建共享记忆、开发约定和独立客户模型，扩展员工与聊天工具。
2. 把已有检索结果导入客户库，完成开发看板、事件和客户独占分配。
3. 接入真实邮箱，完成邮件记录、出站队列、入站事件和追问调度。
4. 完成需求判断、交接卡、接手/交回/继续了解，验证各动作对发信的并发约束。
5. 接入反馈、经验记录和有版本的策略更新；再优化流式体验和模板配置。

后台能力与 HTTP 接口需要同时落地。仅增加路由不能让现有 Worker 从一次性检索变成持续开发；还需增加调度、回信驱动流程和持久化业务状态。新增业务服务应注册为现有聊天工具，HTTP 和 Agent 共用同一权限及状态校验。

## 首期验收场景

- 未确认方向不自动联系；确认旧版本不得启用新版本。
- 两名员工发现同一客户时，仅一个可成为自动跟进负责人。
- 刷新或关闭前端后，服务端仍按计划运行；应用重启不重复发送已确认提交的邮件。
- 接手后不再启动新的自动发信；交回后按最新回信和授权决定下一步。
- 收到明确拒联后停止触达，换员工或恢复开发不能绕过。
- 解雇员工后，公司知识、客户和邮件仍可查询，新员工继承共享知识。
- 每个“值得接手”判断都能追溯客户原话和联系人，缺失采购时间时保留未知。
- 用户反馈形成有来源的学习案例，模型不能把模拟数据或推断写成已核实事实。

本次只形成分析文档，未修改应用代码，未执行真实邮箱授权或邮件发送。
