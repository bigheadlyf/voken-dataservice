# AI 外贸拓客：竞品能力与低资金成本实施方案

调研日期：2026-11-20（香港时间）。范围：公开官网、官方接口文档、用户提供的三张实机截图，以及当前代码库。本文没有购买竞品套餐、批量导出竞品数据库或对供应商准确率做独立审计。

## 决策

沿用当前 FastAPI + MySQL + 单进程 Worker，以 **公开搜索筛选 → 少量付费核验 → 有出处的客户管线 → 开发信审阅 → 自有邮箱发送 → 回复与成交反馈** 为主链路。先交付能反复使用的业务闭环，再用真实转化结果决定是否增加数据订阅。

第一阶段不需要买亿级企业库，也不需要训练专属模型、部署向量数据库或新建消息队列。现有模型接口可以继续使用；搜索与网页内容独立使用 DeepSeek 工具密钥；跨境魔方承担有明确付费价值的交易和联系方式补全。

## 数据能力和 AI 能力要分开

数据层解决“确实有这家公司、做什么、从哪里知道、怎么联系、记录是什么时候的”。模型层解决“理解我方产品与目标角色、生成多语言查询、抽取网页、整理判断和写草稿”。工作流层解决“去重、权限、重试、费用、跟进和反馈”。

仅靠模型记忆不能可靠生成真实联系人、海关交易或仍有效的采购需求。仅有大数据库也不能证明某家企业适合我方具体产品。真正可复用的资产应是逐条带来源的客户记录、人工筛选反馈及实际回复结果。

现阶段区分四类证据：

| 类别 | 可以支持的判断 | 不能支持的判断 |
| --- | --- | --- |
| 搜索摘要 | 值得进一步查看的候选 | 企业身份已核实、当前采购已确认 |
| 官网正文和原文短句 | 页面明确表述的产品、业务与公开联系信息 | 邮箱一定可投递、联系人是最终决策人 |
| 历史进口记录 | 指定时间范围内有相关贸易记录 | 现在仍在采购、准备更换供应商 |
| 真实商务回复 | 已收到某项明确反馈 | 单凭打开追踪就认定强意向或成交 |

当前“证据完整度”是公开规则累加分，不是 AI 成交概率。已有采购信号仍需核对发布日期、截止日期和是否已结束；系统不会把历史海关候选自动改成当前采购需求。

运行结果另提供 `demand_validity` 和 `dated_demand_signal_count`：过期、无日期、今日截止但时刻不明不计入带未来期限依据的采购信号。为兼容旧客户端保留的 `public_demand_count` 不是已验证仍开放需求数。日期依据必须是正文里出现的 ISO 日期和截止原句，不能拿发布日期替代。

## 最低成本的数据组合

| 层次 | 来源与获取方式 | 现金成本控制 | 使用边界 |
| --- | --- | --- | --- |
| 已有资料 | 企业资料、客户自有名单、展会商务名片 CSV 导入 | 不新增数据订阅 | 每条填写来源说明；未知信息保留待核实 |
| 公域发现 | DeepSeek Search + 必要的 Fetch | 同工作空间缓存；限制查询和正文数量 | 搜索不等于完整数据库，来源可能取不到正文 |
| 公域正文 | Search 请求 `need_content=true`，有正文则避免重复 Fetch | 官方说明每次 Search 价格不因结果数量改变 | 仍以实际返回正文为准；不会绕过访问限制 |
| 贸易核验 | 跨境魔方候选列表与单企业交易 | 先筛选，后对少量企业核验 | 记录时间范围、企业 ID 与上游请求 ID |
| 联系方式 | 先使用正文里的公开商务联系信息；不足再向跨境魔方补全 | 仅高价值候选付费；结果复用 | 未检测、有效、无效、不确定需分开；不承诺 SMTP 可达 |
| 新来源 | 客户上传的行业/展会/协会名单，或新 API 适配器 | 先用 CSV 导入验证增益，再评估接口 | 不依赖下载第三方整库或抓取登录墙后的数据 |

DeepSeek 官方说明 Search 和 Fetch 是独立原始 JSON API，分别查找页面和读取正文；请求与计费规则见[官方 Search & Fetch 文档](https://api-docs.deepseek.com/guides/search/)。当前后端已支持搜索带正文、按需补抓与正文上下文上限。

### 为什么先不加更多供应商

这不是数据源越多越好的问题。增加供应商会同时增加字段映射、企业主体匹配、账单核对和故障处理成本。只有当实测表明“某个目标市场的已知缺口”显著影响可联系客户数或回复率时，才应新增对应来源。

建议先做三组受控业务样本：一个历史海关覆盖较好的进口商市场，一个实体渠道市场，以及一个海关弱覆盖的工程/服务类市场。每组保持产品、国家、客户角色和核验口径明确。记录候选数、人工通过数、可联系数、明确回复数和每项真实成本；不要把页面总数作为效果指标。

## 成本计算

截至调研日，DeepSeek 原始 Search 和 Fetch 标价各为 **0.75 美元 / 1000 次成功且有结果的请求**。模型使用另外按 tokens 计价；Flash 有高峰/低谷和缓存命中差异。[官方价格](https://api-docs.deepseek.com/quick_start/pricing/)

以未使用缓存的一次基础任务作示例：

```text
公域接口美元成本 = (有结果 Search 次数 + 有正文 Fetch 次数) × 0.00075
模型美元成本 = Σ(输入 tokens × 对应输入单价 + 输出 tokens × 对应输出单价) / 1,000,000
上游人民币成本 = 美元成本 × 实际结算汇率 + 跨境魔方实际扣费
完整经营成本 = 上游成本 + 服务器/数据库 + 邮箱/域名 + 支付费 + 运维与人工
每条有效客户成本 = 完整经营成本 / 人工验收通过的独立客户数
```

| 示例请求组合 | 公域接口成本，美元 | 不包含 |
| --- | ---: | --- |
| 3 次 Search，搜索已带足够正文，无需 Fetch | 0.00225 | 模型、贸易数据、服务器、触达 |
| 3 次 Search + 2 次 Fetch | 0.00375 | 同上 |
| 当前默认上限 8 次 Search + 5 次 Fetch，全部有结果 | 0.00975 | 同上 |
| 1000 次任务，每次 3 Search + 2 Fetch | 3.75 | 同上；这是情景算例，不是实测账单 |

Search 缓存命中不会新增该次供应商请求；模型仍可能重新调用，因此不能声称缓存任务“免费”。列表查不到结果也可能产生规划模型 tokens。

工作台内的公域人民币成本为可配置的近似估算，默认每次成功请求记 0.006 元；由 `PUBLIC_TOOL_ESTIMATE_MILLI_CNY` 控制，不是实时美元换算或上游确认账单。模型金额仍明确标为未计价，只展示已回传 tokens。

当前增强档沿用项目已有预算：候选列表约 1.5 元，最多两家交易核验约 3 元，最多三家联系方式约 1.5 元，合计预留约 6 元。**这些是代码中的估算参数，未在本次调研验证为当前官方成交价。** 上游回传费用替换估算；费用未知保留预占，异常上涨会停止后续增强，但单次已经发生的费用可能超过预设。套餐网页不能替代 API 账单，批量接口也不应误认为“20 家只收一家费用”。[官方接口计费说明](https://github.com/Upkuajing/upkuajing-trade-company-search/blob/main/SKILL.md#fees)

官方另说明模型服务端联网工具目前不单独收搜索费，但输入的网页内容计入模型 tokens。[联网工具](https://api-docs.deepseek.com/guides/web_tools/) 这是可试验的优化方向。现有工程先保留可控的 Search/Fetch 调用链，因为它便于逐项限制费用、复用结果和保留引文；不能只根据“搜索免费”就断言模型自主联网的总成本更低。

最省现金的私测部署是复用当前常驻服务器与 MySQL，前端由同一个 FastAPI 服务提供，企业邮箱继续使用客户已有服务。没有实际服务器与邮箱报价时，不给一个虚构的“每月固定总价”。私测账号可用本地运营命令开通，减少短信前置支出；点数可对已确认的线下订单做幂等充值，不把赠送点数当作真实收入。

## 当前实现

入口是 `/app`，同域访问业务 API。`WEB_PREFIX` 影响工作台与静态资源入口，不改变 `/api/v1`。

| 环节 | 当前能力 |
| --- | --- |
| 准入 | 既有登录和工作空间隔离；本地运营命令开通私测账号 |
| 我方画像 | 企业名称、产品、优势、联系信息和销售边界；供规划与开发信使用 |
| 找客 | 产品与市场、客户角色、种子官网、排除条件；基础/增强两档 |
| 取证 | 来源 URL、正文短句、检索/正文时间、缓存标记、历史贸易证据 |
| 节约 | 搜索正文复用、按需 Fetch、每空间最多 1000 个缓存条目、可关闭或调节 TTL |
| CRM | 选中线索保存、自有名单导入、保守去重、阶段、标签、下一步、拒绝联系 |
| 开发信 | 使用企业和客户证据异步生成，必须人工审阅；复制或下载 `.eml` |
| 跟进 | 手动记录实际发送、回复、通话、会议与线索反馈；回复可推进阶段 |
| 周期发现 | 1–90 天间隔、1–365 次、仅基础档；停机后不集中补跑，暂停员工同步停用 |
| 成本核对 | 点数账本、原有供应商日志、近 N 天调用/缓存/tokens 汇总；未知费用不伪装为零 |
| 隔离与恢复 | 所有 CRM 读写鉴权；任务幂等、预占/释放与重启恢复沿用现有链路 |

目前没有接入自动邮件发送、收件箱同步、真实在线支付、多人席位、邮件可投递检测或 WhatsApp 官方发送通道。工作台通过“人工审阅 + 自有邮箱 + 反馈记录”完成可用的开发闭环。这是可以开始私测的版本，不能包装成与竞品所有自动化模块完全等价的成熟商业产品。

## 后续投入顺序与验收

1. 先用真实企业产品完成小批量基础档验收，检查主体、产品与角色匹配；只有来源真实且业务相关才计入有效客户。
2. 对同一批人工通过候选做少量增强，测量多得到多少可用商务联系信息，而非只统计增强接口调用成功率。
3. 通过客户自有邮箱发出已审阅邮件，记录明确回复、拒绝、退信和成交；不把打开次数等同于采购意向。
4. 若手动收发成为瓶颈，再接入一个带退信与拒绝联系处理的邮箱通道。应先保障发件主体、域名配置和凭据存储，然后做发送队列与回复归档。
5. 若团队协作成为瓶颈，再加席位与权限；若并发或可用性有真实压力，再分离 Worker。当前不要用多进程绕过单 Worker 的运行假设。

验收关注的分母：候选去重后企业数、人工核验数、可联系数、实际发送数。经营指标至少分清“线索相关”“历史采购”“明确需求”“回复”“成交”，每项都记录时间与证据。数据采购是否划算，应由这些指标和现金账单共同决定。
